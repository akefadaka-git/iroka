## 1. Executive disposition

K-04 is not closed by the existing SQLite hash chain. The current implementation provides useful local tamper evidence, but a privileged actor who can alter the database file can remove the final rows, replace the local chain, or restore an older database image. The local append-only triggers are database controls, not an independent trust boundary.

This design establishes a separate, independently administered checkpoint and witness plane. It is intended to make previously committed audit history externally detectable if the primary host or database is altered, rolled back, truncated or presented with a conflicting history.

**This document is design only.** It does not change the audit implementation, database schema, production configuration, signing keys, witness infrastructure, retention policy or authorization behavior. The design branch is separate from the previously verified correction branch. No merge, deployment or A2 closure is authorized by this document.

## 2. Existing implementation — verified source facts

The current implementation is in `crates/iroka-kernel/src/audit_store.rs` and `crates/iroka-kernel/src/assurance.rs`.

Current controls:
- SQLite WAL mode and `synchronous=FULL`.
- Unix database file creation mode `0600`; symlinks and group/world-readable existing files are rejected.
- `BEGIN IMMEDIATE` serializes append transactions within the connection.
- Unique event IDs and SQLite triggers reject ordinary UPDATE and DELETE statements.
- Each event hash includes the previous event hash and the event's current content fields under domain `IROKA:G11:AUDIT-EVENT:V1`.
- Startup and explicit verification recompute the local hash chain.
- Audit sink failure converts an otherwise positive authorization decision to `ESCALATE`.

Limitations visible in the current source:
1. The hash input does not include the database sequence number, a stream identifier, a tenant identifier, or an explicit event-schema version.
2. The verifier checks links between rows that remain present, but has no trusted external high-water mark. Deleting a terminal suffix can leave a shorter chain that verifies.
3. The sequence is generated by SQLite and is not independently committed or witnessed.
4. Triggers can be removed by an actor able to alter the database schema or replace the database file.
5. `head()` reports a local sequence/hash pair; it does not prove that the pair is the newest accepted history.
6. No independent signer, witness receipt, remote append-only log, anti-equivocation protocol, checkpoint recovery procedure or checkpoint freshness policy is implemented.
7. `AuditEvent` has no tenant or stream field. The present adapter is one local ordered chain, not proof of tenant-separated audit streams.
8. The current chain is not a Merkle tree. Efficient logarithmic inclusion proofs are not available from this format.

These limitations are the reason K-04 remains OPEN. They are not fixed by the K-02/K-03 concurrency changes or by the successful Rust test run.

## 3. Security objectives and threat model

### 3.1 Required security objectives

The checkpoint system must provide evidence of:
- **Integrity:** changes to an already checkpointed event prefix are detectable.
- **Completeness to a checkpoint:** truncation or rollback below an externally accepted sequence is detectable.
- **Ordering:** a later checkpoint commits to a strictly later sequence and the exact previous checkpoint.
- **Anti-replay:** an old checkpoint cannot be accepted as the current head.
- **Anti-equivocation:** one stream cannot silently present two different histories at the same checkpoint position to honest witnesses.
- **Independent custody:** the primary audit database administrator cannot unilaterally rewrite the witness's accepted history or signing key.
- **Verifiability:** a verifier can validate checkpoint signatures and witness receipts without trusting the primary audit database.
- **Recoverability:** a restored database can be reconciled against the latest independently accepted checkpoint without resetting or lowering the witness high-water mark.
- **Privacy minimization:** witnesses receive commitments and bounded metadata, not raw audit event contents.

### 3.2 Threats addressed

- Privileged application or database operator modifies or replaces the SQLite database.
- Backup restore rolls the audit database back to an earlier valid state.
- An attacker deletes the final events and presents a shorter but locally valid chain.
- A host presents a forked history to different reviewers or witness endpoints.
- Checkpoint messages are replayed, reordered, duplicated or signed with an unknown/revoked key.
- The primary audit host is unavailable while the independent witness remains available.
- A checkpoint signing key is compromised or requires rotation.

### 3.3 Explicitly not solved by checkpointing alone

- An event never emitted by the application cannot be recovered from a hash chain.
- A compromised application can fabricate events before they are committed.
- A malicious quorum of all independent witnesses can collude.
- Hash commitments do not establish the truth of event fields.
- A signed checkpoint does not prove that the system clock was correct.
- A checkpoint cannot recover deleted event payloads; it detects inconsistency and supports recovery from separately protected backups.
- This design does not provide legal non-repudiation, regulatory certification, or proof of bare-metal security without separate controls and evidence.

The event-generation coverage, privileged side-effect audit coverage, tenant isolation, clock discipline and backup recovery process remain separate assurance obligations.

## 4. Target architecture

Separate the audit lifecycle into four trust boundaries:

1. **Event producer / local append adapter** — emits structured events and commits them to the local audit stream.
2. **Checkpoint builder and signer** — reads a consistent committed prefix, verifies the local chain, constructs a canonical checkpoint and requests a signature from a separately protected signer. The signer key must not be stored in the audit database or ordinary application configuration.
3. **Independent witness service(s)** — independently validate the signed checkpoint, enforce stream sequence and predecessor continuity, persist accepted checkpoint digests in an append-only ledger, and issue signed receipts.
4. **Verifier / recovery tooling** — compares local events, signed checkpoints and witness receipts; reports integrity, rollback, fork, freshness and recovery status.

The witness service must be administered in a separate security and operational boundary from the primary audit database. A second process, container or database on the same host under the same administrator is not independent custody.

### 4.1 Trust boundary diagram

Protected operation
       |

No private signing key is placed in this repository, SQLite database, CI variables, application image or ordinary host filesystem.

## 5. Checkpoint protocol proposal

### 5.1 Stream identity

Every checkpoint belongs to a stable, opaque `stream_id`. A stream represents one explicitly governed audit history.

The first implementation must not invent tenant isolation that the current `AuditEvent` schema does not provide. Before enabling multi-tenant streams, Owner-approved contracts must define:
- tenant identity source and canonical tenant identifier;
- whether each tenant has a separate stream or a tenant-scoped partition within a shared witness ledger;
- treatment of platform/global security events;
- stream creation, closure, transfer and retention rules;
- cross-tenant access controls for checkpoint and event verification.

For a single-node/single-stream pilot, use one provisioned opaque stream ID. Do not treat a caller-supplied tenant string as authenticated tenancy.

### 5.2 Canonical checkpoint payload

Proposed logical fields for `IROKA-AUDIT-CHECKPOINT-V1`:

| Field | Meaning |
|---|---|
| `protocol` | Fixed protocol identifier and version |
| `stream_id` | Provisioned opaque audit-stream identity |
| `checkpoint_number` | Strictly increasing checkpoint number for this stream |
| `first_sequence` | First sequence covered by the stream/checkpoint range |
| `last_sequence` | Highest committed event sequence included |
| `event_count` | Count of events committed through this checkpoint |
| `head_event_hash` | Hash of the last event in the committed prefix |
| `previous_checkpoint_digest` | Digest of the immediately preceding checkpoint; fixed genesis value for the first checkpoint |
| `chain_format` | Event-chain format identifier, initially V1 |
| `hash_algorithm` | Explicit algorithm identifier; SHA-256 for the current chain |
| `created_at` | Producer timestamp, informational and not independently trusted |
| `signing_key_id` | Exact checkpoint-signing key identifier |

The signed representation must use the deterministic CBOR rules selected by the approved canonical interchange contract (OD-07). Sign the exact canonical bytes with Ed25519 and a domain-separated checkpoint context. The checkpoint digest is computed over the canonical payload bytes, not over a JSON rendering or an implementation-dependent serializer output.

The first checkpoint commits to the current V1 chain head without rewriting historical event hashes. Future event-chain format changes require a separately versioned migration and explicit compatibility rules.

### 5.3 Witness receipt

For each accepted checkpoint, a witness returns a signed receipt containing at least:
- witness protocol/version and witness identity;
- stream ID;
- checkpoint number and checkpoint digest;
- accepted last sequence and event head hash;
- previous accepted receipt/checkpoint digest;
- witness-assigned acceptance time;
- monotonically increasing witness log index;
- witness signing key ID.

A receipt means only that the named witness accepted and durably recorded that checkpoint under its stated policy. It does not attest to the truth or completeness of the underlying application events.

### 5.4 Acceptance rules

A witness must reject a checkpoint unless all of the following hold:
1. The checkpoint canonical encoding and protocol version are supported.
2. The checkpoint signature verifies under an explicitly trusted, currently valid signing key.
3. The stream ID is provisioned and authorized for that signer.
4. The checkpoint number is exactly the next permitted number, subject to an explicitly specified idempotent retry rule.
5. The last sequence is strictly greater than the prior accepted sequence (except a byte-identical idempotent replay).
6. The previous checkpoint digest equals the witness's accepted head for that stream.
7. The event count and sequence progression satisfy the stream's declared continuity rules.
8. The checkpoint does not use an expired, revoked or unknown key.
9. No conflicting digest has already been accepted for the same stream/checkpoint number.

A byte-identical replay returns the original receipt. A different digest at an already accepted checkpoint number is an anti-equivocation incident, not a normal retry.

### 5.5 Multiple witnesses and anti-equivocation

**Recommended topology for Owner decision:** three independently administered witnesses, with a two-of-three receipt quorum for a checkpoint to be considered externally anchored. Witnesses should not share the same cloud account, administrator credentials, signing key, backup operator or control plane.

Each witness keeps its own append-only per-stream history and periodically exchanges checkpoint heads with the other witnesses. A witness must expose verifiable consistency from its prior accepted head. Conflicting signed checkpoints for the same stream and checkpoint number trigger an incident and suspend automatic acceptance pending reconciliation.

A two-of-three topology is a recommendation, not an approved policy. The Owner must select witness count, quorum, independence criteria and outage behavior before implementation. A single independent witness is simpler but cannot robustly detect all split-view/equivocation scenarios if that witness is compromised or unavailable.

### 5.6 Checkpoint cadence and freshness

The checkpoint builder should trigger when either:
- a configured maximum elapsed interval has passed since the last quorum-accepted checkpoint; or
- a configured maximum number of new events has accumulated.

A manual checkpoint operation must also be supported for incident response, before planned maintenance, before backup/restore, and before a release or high-impact governance operation where policy requires it.

No numeric interval, event-count threshold or maximum unanchored window is selected in this document. These are risk and operational decisions requiring Owner approval. The system must expose:
- latest local event sequence/hash;
- latest locally built checkpoint;
- latest witness-accepted checkpoint per witness;
- quorum status;
- age of the last quorum-accepted checkpoint;
- number of unanchored events;
- last successful witness contact and last error.

### 5.7 Fail-closed and degraded operation

Local event append remains synchronous and fail-closed as it is today: an audit append failure must not permit a positive protected authorization result.

Remote checkpointing is asynchronous so that a network outage does not turn every authorization into a synchronous external dependency. However, the system must not silently treat unanchored events as externally protected.

When checkpoint freshness exceeds the Owner-approved maximum:
- emit a high-severity assurance alert;
- mark audit anchoring state as DEGRADED / STALE;
- block operations designated by policy as requiring fresh external anchoring;
- preserve local append and retry state without discarding events;
- never fabricate a witness receipt or lower the recorded high-water mark.

The Owner must decide which operation classes require fresh quorum anchoring and whether a bounded emergency override exists. Any override must be explicit, time-bounded, scoped, separately signed and auditable. No override is approved here.

## 6. Event-chain evolution and proof model

### 6.1 Preserve V1 history

Do not rewrite existing V1 hashes in place. The initial checkpoint anchors the existing `(sequence, event_hash)` head and identifies `chain_format=IROKA:G11:AUDIT-EVENT:V1`.

For future events, a V2 event envelope should include at least:
- stream ID;
- tenant scope where a trusted tenant contract exists;
- sequence number;
- event schema version;
- previous event hash;
- canonical event payload digest;
- event hash algorithm and domain/version.

The exact V2 encoding must be separately specified and tested before migration. Historical V1 verification remains available for the retained V1 prefix.

### 6.2 Proof of a range

For V1, verification of an event range between two trusted checkpoints requires replaying the linked event records between the prior anchored head and the later checkpoint head, with the necessary predecessor hash. This is linear in the number of events in the range.

A Merkle accumulator or transparency-log tree may be introduced if independent event inclusion proofs and large-scale range verification are required. It must not be described as present in the current implementation. If selected, its tree construction, leaf encoding, domain separation, inclusion proofs, consistency proofs and test vectors require a separate normative specification.

### 6.3 Completeness limits

A checkpoint proves that a particular prefix commitment was accepted by independent witnesses. It does not prove that every relevant system action generated an event. The assurance plan must inventory protected side effects and require audit emission at the decision/commit boundary, with failure semantics and independent tests for every high-risk path.

## 7. Key custody, rotation and compromise

- Checkpoint signing keys are distinct from Owner approval keys, issuer credential keys and trust-root keys.
- Private checkpoint keys remain outside the repository and outside the primary audit host.
- Prefer an offline signer or hardware-backed KMS/HSM with non-exportable private key material and narrowly scoped signing authorization.
- The signer accepts only validated checkpoint payloads from an authenticated builder identity; it does not sign arbitrary caller-provided bytes without policy checks.
- Public verification keys, key IDs, validity periods and revocation status are distributed through a signed, versioned trust policy.
- Rotation uses an explicit overlap window and dual-verification period; revocation and emergency replacement are independently governed.
- Witness receipt keys are separately held by each witness.
- Compromise requires freezing affected signing authority, preserving all receipts and evidence, issuing a separately authorized key-status update, and reconciling the latest independently witnessed checkpoint. Never reset the witness ledger to make a replacement key appear authoritative.

Exact KMS/HSM vendor, jurisdiction, key ceremony, backup/recovery and operator separation remain open procurement and governance decisions.

## 8. Witness storage and operations

Each witness must provide:
- durable append-only checkpoint/receipt storage;
- authenticated submit and read APIs;
- per-stream monotonic state and uniqueness constraints;
- independently controlled signing keys;
- immutable or retention-locked backups;
- export of signed receipts and checkpoint history;
- monitoring for stale streams, invalid signatures, sequence gaps, forks and key expiry;
- documented incident, restore, key-rotation and operator-access procedures.

A witness implementation may use a transparency log or append-only object store with retention lock, provided it can prove continuity and prevent an ordinary administrator from silently rewriting accepted history. A second SQLite file on the same host is not an acceptable independent witness.

No blockchain is required for this design. A conventional independently administered append-only transparency log with signed receipts, anti-equivocation checks and independently retained evidence is the recommended starting point. Blockchain would add consensus, governance, privacy and operational complexity without automatically solving event completeness or trusted event generation.

## 9. Restore, rollback and fork handling

On startup, restore or periodic reconciliation:
1. Verify the local event chain from its genesis or last trusted checkpoint.
2. Fetch the latest signed checkpoint and receipts from each configured witness.
3. Validate signatures, stream identity, witness quorum and checkpoint predecessor continuity.
4. Compare the local sequence/hash against the latest accepted checkpoint.
5. If local sequence is lower than the witnessed sequence, or the hash at the witnessed sequence differs, quarantine the stream as ROLLBACK_OR_TAMPERED.
6. If the local chain extends the witnessed checkpoint, verify every intervening event and schedule a new checkpoint.
7. If witnesses disagree, mark WITNESS_FORK / QUORUM_UNAVAILABLE and stop automatic acceptance.
8. Preserve the evidence and incident record; do not truncate, rewrite, reinitialize or reset the witness high-water mark.

Recovery must restore event payloads from a separately protected backup and replay/verify them against the externally accepted checkpoint. A checkpoint is a commitment, not a backup.

## 10. Data protection and Amharic-first requirements

- Checkpoint and receipt formats are language-neutral machine formats; human-facing diagnostics must be Amharic-first with English available.
- Preserve original UTF-8 event text and Ethiopic code points. Do not transliterate or normalize source strings destructively.
- Witnesses receive hashes, opaque stream IDs, sequence data, protocol metadata and key IDs only. Do not send subject names, resource labels, document contents, credentials, or raw event payloads unless a separately approved evidence-export workflow explicitly requires them.
- Human-facing times should follow the approved Ethiopia profile and Ethiopian-calendar presentation rules; machine timestamps must have an explicit UTC representation and must not collapse date-only values into instants.
- Witness retention, lawful access, cross-border data handling and evidence export must be assessed independently for each African regional profile. Do not infer that one Africa-wide policy is valid for every jurisdiction.

## 14. K-04 exit criteria

K-04 may be proposed for closure only when:
1. All Owner decisions in §13 have explicit recorded dispositions.
2. A versioned canonical checkpoint and receipt specification is approved.
3. Signer and witness trust boundaries are independently administered and evidenced.
4. Witness anti-rollback, idempotency and anti-equivocation behavior is implemented.
5. Local chain verification is bound to external accepted high-water marks.
6. Restore, truncation, fork, outage, key rotation and compromise exercises pass.
7. Event coverage for protected side effects is inventoried and tested.
8. Privacy, tenant separation, retention and regional requirements are verified.
9. Exact-SHA build/test evidence and independent operational evidence are retained.
10. A separate Owner acceptance closes K-04.

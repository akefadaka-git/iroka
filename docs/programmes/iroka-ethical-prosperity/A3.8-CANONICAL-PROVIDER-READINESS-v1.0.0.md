## 1. Purpose

A3.8 requires exact-provider binding and cross-domain adversarial verification. This record distinguishes capabilities that already exist from adjacent capabilities that are still missing. It prevents a credential from being mistaken for a content approval, an Owner approval from being mistaken for an organization delegation, or a decision audit stream from being mistaken for a memory lifecycle stream.

## 2. Existing providers and their exact semantics

| Provider | Available capability | Does not prove |
|---|---|---|
| G01 | Ed25519 credential verification, trusted issuer/key snapshots, exact audience and validity, fail-closed revocation | Reviewer designation or approval of a specific record |
| G02 | Direct Owner-signed exact-scope approvals, revocation and replay protection; tenant membership | Organization-scoped delegation or reviewer authority |
| G11 | Append-only, hash-chained decision audit | Memory lifecycle events or cross-database atomicity |

These existing capabilities are reusable only within their documented contracts.

## 3. Blocker A — G01 reviewer-proof verifier

The inspected G05 integration port G01ReviewerProofAuthority is an interface, not a concrete G01-owned verifier. The missing verifier must bind:
- current reviewer principal to the currently designated signing key;
- canonical signing bytes and a dedicated signing-domain separator;
- tenant, organization, reviewer, designation version, memory ID, record version, content digest, purpose and classification;
- proof validity, replay protection and current credential/key revocation at proof use.

A G01 credential authenticates a principal but does not prove that the principal approved a specific record. A G02 Owner approval is not a substitute. Until the G01-owned verifier exists, reviewer approval remains denied.

## 4. Blocker B — G02 organization-scoped delegation

The inspected Kernel security store contains tenant membership and policy/revocation state, but no canonical organization-delegation registry or designation/revocation action. Global capability and tenant membership do not establish an organization role.

The authoritative organization source/provider and its governance owner have not been identified in the inspected repository evidence. A future provider must bind and revalidate the exact versioned delegation tuple, including tenant, organization, actor, delegation ID/version, action and reviewer scope, and must specify its consistency/linearization behavior.

This programme must not invent a second organization-authority registry or accept a caller-asserted role.

## 6. Safe implementation boundary

- Reuse G01 credentials/revocation, G02 Owner approval and G11 decision audit only for their established semantics.
- Keep reviewer approval and organization-scoped durable activation fail-closed until canonical providers are implemented and independently tested.
- Do not add duplicate identity, reviewer, consent, delegation, memory or audit registries.
- Do not treat an unmerged branch as a canonical integrated provider.
- Preserve the A2 VERIFIED-CLOSED baseline and its open decision gates.

## 9. Owner decision — organization-authority model A (2026-11-10)

The Owner selected **A — Owner-governed authority**. G02 is the single canonical authority provider for organization creation, administrator appointment, scoped delegation and revocation, all through valid Owner-signed, versioned commands. G01 remains identity/credential verification; G05 consumes verified G02 decisions and must not maintain a competing organization-role registry; G11 records governance evidence without becoming an authorization source.

The selected model is specified in [G02-OWNER-GOVERNED-ORGANIZATION-AUTHORITY-CONTRACT-v0.1.0.md](../../architecture/G02-OWNER-GOVERNED-ORGANIZATION-AUTHORITY-CONTRACT-v0.1.0.md). This decision resolves the previously open question of the governance owner and authority model. It does not claim the G02 provider is implemented. Provider implementation and adversarial verification remain in progress; A3.8 therefore remains PARTIAL until all exit criteria, including the separate G01 reviewer-proof provider and G05/G11 integration reconciliation, are met.

### G02 organization-authority provider — 2026-11-11

The G02 Owner-governed organization-authority candidate is implemented on the integration branch in PR #50:
- dedicated `IROKA:G02:ORGANIZATION_AUTHORITY:V1\0` signing domain with deterministic JCS bytes and strict payload/scope validation;
- Owner-key identity, validity, signature and revocation checks, including transactional signer-revocation recheck;
- canonical organization and designation state in the existing Kernel security store;
- immutable organization-to-tenant binding, monotonic versions, explicit designation revocation, and organization suspension/reactivation;
- resolver consumes G01 `VerifiedPrincipal` and `TenantContext`, rechecks live membership/version and reads current organization/designation state on each decision;
- adversarial tests cover cross-tenant/cross-principal isolation, freshness, capability denial, tenant binding, designation revocation, organization lifecycle, signature tampering, replay, expiry, future-issued commands and revoked Owner keys.

**Delegation provider:** Owner-signed, versioned delegation grants are now persisted in the canonical G02 security store. The grant binds tenant, organization, delegator, delegate, delegation ID, exact capability set, version and expiry. Resolution revalidates the delegate's current G01 tenant membership, active organization, live delegator designation, the delegator's `organization.designation.delegate` capability, and that every delegated capability remains within the delegator's current capability set. Grants are Owner-created and Owner-revoked; the resolver returns an immutable `DelegationContext`. The delegated-administrator mutation/command-signing path is **not implemented**; a grant cannot currently be used to sign designation mutations. Default subdelegation remains fail-closed.

### G01 cryptographic reviewer-proof provider — 2026-11-11

A bounded G01 reviewer-proof verification boundary has been added in `crates/iroka-kernel/src/reviewer_proof.rs` and specified in [G01-REVIEWER-PROOF-CONTRACT-v0.1.0.md](../../architecture/G01-REVIEWER-PROOF-CONTRACT-v0.1.0.md).

- Dedicated NUL-terminated `IROKA:G01:REVIEWER_PROOF:V1` domain and deterministic JCS signing bytes.
- Proof binds verified issuer, subject and credential ID to reviewer ID, reviewer key ID, approval ID, tenant, organization, capability, resource, policy version and short issue/expiry window.
- Required authoritative `ReviewerKeyBindingResolver` checks the exact identity/key tuple and returns key validity, current credential/key revocation flags and the time of its check; missing, stale or revoked bindings fail closed.
- Ed25519 signature, exact expected scope, maximum 300-second proof TTL, 30-second binding freshness and one-time proof ID consumption are enforced.
- One-time consumption is persisted in the existing Kernel security store with a unique `(issuer, credential_id, proof_id)` key. No separate reviewer registry is introduced.
- Unit tests cover exact scope and principal binding, signature integrity, key revocation, expiry/future issue time and replay.

**Boundary:** the authoritative issuer-side reviewer-key binding adapter is an explicit trusted dependency and has not been provisioned or independently reviewed. This implementation does not designate reviewers, verify community authority, or approve Maale content. G05 is not yet wired to consume `VerifiedReviewerProof`; its integration must compare every proof field to its own canonical designation/approval state and consume it once. No G05/G11 branch is treated as merged or canonical.

**Current G01 verification candidate:** implementation and test evidence is being verified against the exact current PR #50 head; do not mark this provider VERIFIED-CLOSED until the exact-head workflow is successful. A3.8 remains PARTIAL, and A4 remains NOT RUN.

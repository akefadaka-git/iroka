# C1.5 — Isolated Compiler, Test and Debugger Execution Contract

Status: A1/A2 contract frozen for implementation.

## A2 reconciliation findings

- The kernel authorization service explicitly states that ALLOW is a decision, not an execution grant.
- The current kernel has G01 credential verification, G02 signed Owner approval, durable SQLite security state and audit, but no G09 execution-grant exchange.
- C1.4 correctly stopped at in-memory patch preview because no G09 grant existed.
- C1.5 must add G09 as a kernel-owned, one-time, short-lived grant boundary before any sandbox command or persistent workspace write can run.
- No unsandboxed fallback, shell command string, remote execution endpoint or production key may be introduced.

## G09 execution grant

A grant may be issued only from an opaque `GovernedDecisionEvidence` produced inside the kernel after:
- G01 principal and constitutional baseline validation;
- policy evaluation for a capability that requires Owner approval;
- successful G02 signed Owner approval with exact subject/capability/resource/policy scope;
- successful durable audit append.

G09 grants are:
- bound to subject, capability, repository, exact source revision, sandbox identity, action digest and policy version;
- short-lived (maximum 60 seconds), single-use and replay-protected;
- persisted in the kernel SQLite security store with a unique decision ID, scope digest, token hash, issued/expiry timestamps and consumed state;
- represented by opaque non-Clone/non-serializable types; tokens are redacted from debug output;
- consumed atomically before a sandbox action begins.

An ALLOW `Decision`, raw request, Owner approval object, or model response alone must never be accepted as a grant.

## Sandbox boundary

The execution broker accepts only a consumed G09 grant and a typed, allowlisted tool invocation. It must:
- run in a separate OS process with a verified isolation backend;
- expose only the pinned workspace snapshot as writable input;
- mount runtime/toolchain inputs read-only;
- disable network access and prevent access to host home directories, credentials, SSH agents, environment secrets and unrelated repositories;
- avoid shell parsing; pass executable and arguments as separate values;
- enforce wall-clock, CPU, memory, process-count, output-byte and workspace-size limits;
- capture stdout/stderr and structured exit status;
- kill the process tree on timeout/cancellation;
- fail closed if the isolation backend is unavailable or its isolation prerequisites cannot be verified.

No package manager installation, registry access, automatic dependency download or privileged container mode is permitted.

## Tool profiles

Toolchain profiles are explicit, versioned and language-specific. Initial profiles may cover installed Rust, Python and Node/TypeScript toolchains. The broker must report unsupported or unavailable tools as NOT RUN; it must not guess commands or silently run on the host. Debugger mode uses an allowlisted debugger command inside the same sandbox and shares the same grant, resource and time limits.

## Acceptance

A1/A2 acceptance requires opaque decision evidence, G09 issuance/consumption/replay/expiry/scope tests, durable store tests, command allowlisting, sandbox argument construction, isolation prerequisite checks, timeout/output/resource enforcement, no-network policy and fail-closed tests. A real sandbox integration test is required before claiming isolated execution is production-ready.

## Governance

C1.5 may add the kernel G09 boundary and sandbox broker, but it does not authorize merge, signing, release or deployment. No production keys or external services are used. Persistent workspace writes remain disabled until an execution grant is consumed by the isolated workspace adapter.

# C1.4 — Governed File Editing, Patch Review and Rollback Contract

Status: A1/A2 contract frozen for implementation.

## A2 reconciliation findings

- C1.3 emits validated, single-target unified-diff proposals but deliberately never applies them.
- The kernel exposes the canonical G02 `OwnerApprovalVerifier`, signed `SignedOwnerApproval` payloads and a durable, replay-protected SQLite security store.
- The kernel's authenticated authorization API explicitly documents that an ALLOW decision is not an execution grant; G09 must exchange decision evidence for a short-lived execution grant.
- No G09 execution-grant API or trusted workspace-write adapter is present in the inspected kernel surface.
- C1.4 must not invent a parallel Owner registry, treat a model response as approval, or interpret G02 ALLOW as permission for persistent filesystem writes.

## Scope

C1.4 implements:
- strict review of C1.3 validated patches against an immutable, revision-pinned repository snapshot;
- protected-path and path-traversal policy;
- deterministic unified-diff application in memory with base-content and hunk-context verification;
- patch digest and before/after content hashes;
- exact-scope, one-time G02 Owner approval through the kernel's existing verifier;
- an in-memory preview transaction with explicit rollback to the exact original snapshot.

## Owner approval binding

The approval scope binds the requesting subject, fixed capability `coding.patch.preview`, policy version, repository identity, exact source revision and SHA-256 digest of the complete patch proposal. The existing kernel verifier must validate the Ed25519 Owner signature, key validity, expiry, revocation and replay protection. No local substitute or unsigned approval flag is permitted.

A verified preview approval is not a G09 execution grant and cannot authorize persistent file writes.

## Protected paths

Default-deny protected areas include:
- `.git/`, `.github/workflows/`, `.github/actions/`;
- secrets, credentials, private-key, certificate and environment-file paths;
- G01/G02/kernel governance, identity, trust, approval, security-store and audit implementation files;
- lockfiles and other dependency-resolution artifacts unless a later, separately scoped policy explicitly permits them.

Path checks are repository-relative, reject absolute paths, drive prefixes, traversal, control characters and symlinks, and are repeated at review and preview-application boundaries.

## Patch application

The patch engine supports one file per proposal, exact old/new path headers, unified-diff hunks and strict context matching. It rejects malformed, overlapping, out-of-order, truncated, multi-file, binary and unsupported no-newline-marker patches. It does not invoke `git apply`, shell commands, editors, package managers or compilers.

A preview transaction stores the original and proposed snapshots. Rollback returns the byte-for-byte original snapshot. There is no commit or persistent-write method in C1.4.

## Explicit G09 boundary

Persistent workspace writes are NOT IMPLEMENTED in C1.4 because the inspected kernel has no G09 execution-grant exchange API. Adding a filesystem writer that relies only on G02 approval or an ALLOW decision would violate the kernel's stated boundary. C1.5/G09 integration must supply an independently verified, short-lived execution grant before persistent writes can be enabled.

## Acceptance

A1/A2 acceptance requires deterministic patch parsing, path protection, source/hash binding, one-time G02 approval verification, stale-base rejection, preview isolation, exact rollback and adversarial tests. Exact-HEAD CI must pass before C1.4 closure. No merge, release or deployment is authorized.

# C1.3 — AI Task Planner and Structured Code-Generation Contract

Status: A1/A2 contract frozen for implementation.

## Purpose

Provide a provider-neutral planning and code-generation boundary that converts an engineering request plus repository evidence into a validated, reviewable plan and structured patch proposals. The planner and generator propose work; they do not authorize, apply, execute, commit or deploy it.

## Inputs

A planning request contains:
- a non-empty task description with explicit size limits;
- a pinned repository source revision;
- a bounded repository index;
- evidence snippets with repository-relative paths, positive line ranges and bounded excerpts;
- explicit constraints and acceptance criteria.

Evidence and repository text are untrusted data. They must never be interpreted as system instructions or authorization.

## Plan contract

A plan is versioned and contains:
- stable plan and task identifiers;
- a concise objective and explicit assumptions;
- ordered steps with stable identifiers;
- step action classification (inspect, analyze, edit, test, verify, or request approval);
- explicit step dependencies;
- target paths and evidence references;
- expected outputs and acceptance criteria;
- risk classification and required capability labels.

Validation must reject:
- unknown schema versions, malformed identifiers and empty plans;
- duplicate step identifiers, missing dependency references, self-dependencies and dependency cycles;
- evidence paths absent from the pinned repository index, unsafe paths or invalid line ranges;
- target paths that are absolute, traverse outside the repository or contain control characters;
- mutating plans that omit the mandatory Owner-approval boundary;
- plans exceeding configured step, string, evidence or total-size limits.

A valid plan is still only a proposal. Validation does not create a G02 grant or execution capability.

## Structured code-generation contract

A generation request is bound to:
- the plan/task/step identifiers;
- the pinned source revision;
- a registered language identifier;
- one repository-relative target path and explicit create/modify/delete operation;
- bounded evidence/context and generation constraints.

A response contains a matching request identifier, summary, diagnostics and one or more structured changes. Each change contains a repository-relative path, explicit operation, unified-diff text and rationale. Validation rejects mismatched request IDs, unsafe paths, duplicate targets, invalid create/modify/delete preconditions, malformed patch headers, empty output and output exceeding per-patch or aggregate limits.

Generated patches are untrusted proposals. C1.3 never applies them. C1.4 owns diff review, protected-path policy, application, authorization and rollback.

## Provider boundary

PlanningProvider and CodeGenerationProvider are synchronous, provider-neutral traits. The orchestrators invoke a supplied provider, validate its response and return an opaque validated result.

An optional Ollama-compatible adapter is implemented for local inference. It is restricted to a loopback TCP endpoint (default 127.0.0.1:11434), uses bounded HTTP request/response sizes and timeouts, and never contacts remote hosts or executes a local command. The operator must install and start Ollama and provide an already-available model name; the repository does not download models or store credentials. Tests use a local mock HTTP server.

Remote model-provider transport, credentials, retries and production deployment remain separate adapters. A provider failure, malformed response or validation failure is fail-closed. No fallback may silently convert invalid model output into an accepted plan or patch.

## Governance and exclusions

- Planning and generation are read-only proposal operations.
- No filesystem writes, shell commands, compilation, test execution, network access, dependency installation, commit, merge or deployment.
- No model response may modify G01/G02/G11 governance or Owner authority.
- Every mutating step must preserve a mandatory Owner-approval requirement.
- C1.4 is the sole owner of governed patch application and rollback.
- No merge, signing, release, deployment or production activation is authorized by this contract.

## Acceptance

A1/A2 acceptance requires typed contracts, bounded validation, deterministic validation errors, dependency-cycle checks, evidence/path binding, provider-boundary tests and structured patch-response validation. Exact-HEAD CI and implementation closure are required before C1.4 begins.
